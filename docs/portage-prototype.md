# Porter une page du prototype

> Objectif : une **représentation exacte et complète** du prototype, alimentée par de vraies données.
> Le prototype (`prototype/`, servi par `pnpm prototype` sur http://localhost:5173) est la référence visuelle et fonctionnelle.
> La page Contact (`apps/web/src/pages/contact.astro`, `src/scripts/contact.ts`) est l'exemple complet à suivre.

## 1. Méthode

1. **Lire la page du prototype** : son HTML, sa feuille de style, son script et ses fichiers de données (tableau ci-dessous). Repérer ce qui est simulé (données `*-data.js`, états du panneau Tweaks) et ce qui doit venir de l'API.
2. **Styles** : recopier la feuille de style de la page **sans la modifier** dans `apps/web/src/styles/` et l'importer dans la page après le gabarit (`import Base…` puis `import '../styles/x.css'`). `styles.css`, `commun.css` et `etats.css` sont déjà chargés par le gabarit. Un ajout nécessaire va dans `socle.css` ou un fichier nouveau.
3. **Balisage** : créer la route (tableau ci-dessous) avec `layouts/Base.astro` et y recopier le contenu de `<main>`. Reporter :
   - les classes de `<body>` (`classeCorps`), ses attributs `data-*` (`donneesCorps`), la classe de `<main>` (`classeMain`) ;
   - les attributs `data-*` propres à la page posés sur `<html>` (`reglages`) avec leurs **valeurs par défaut** : ce sont les variantes retenues ; le panneau Tweaks n'est pas repris ;
   - les icônes du sprite de la page (`icones`) ; une icône dessinée autrement que dans `src/lib/icones.ts` passe par `remplacementsIcones` ;
   - les liens : `ROUTES` (`src/lib/navigation.ts`) à la place des fichiers `.html`.
4. **Données** : remplacer les fichiers `*-data.js` par l'API. Ce qui structure la page et compte pour le référencement est rendu côté serveur (composants Astro) ; ce qui réagit aux actions reste dans le script de page. Garder la forme des données du prototype quand c'est possible : le portage du script en est simplifié.
5. **Script** : porter le JavaScript de la page en TypeScript dans `src/scripts/<page>.ts`, avec les outils de `src/scripts/commun/` (`$`, `$$`, `icon`, `t`, `toast`, `corrigerTypographie`, `etats`). Les simulations disparaissent : envoi réel à l'API, erreurs RFC 9457 affichées champ par champ, état du bouton pendant l'envoi.
6. **États** : la personne qui consulte vient du serveur (`Astro.locals.etat`, `data-pour` dans le HTML, `etats.peut()` dans les scripts). Les états propres à la page (brouillon, sujet fermé, liste vide…) se déduisent des données.
7. **Vérifier côte à côte** avec le prototype, à 1280, 820 et 375 px de large, dans les états concernés (visiteur, membre, lecture seule, auteur, modération), clavier et animations réduites compris. Noter tout écart volontaire dans le registre.

## 3. Repères

- Le prototype écrit les adresses des pages (`fiche-creation.html?id=…`) ; le site suit le plan du site (`/creations/12-portrait-editorial`). L'identifiant numérique fait foi, la partie texte sert la lisibilité : une adresse dont le texte ne correspond plus redirige vers la bonne.
- `commun.js` montait l'en-tête, le compte et le pied de page dans le navigateur ; ils sont désormais rendus par le serveur (`SiteHeader.astro`, `SiteFooter.astro`, `EtatBandeau.astro`). Les comportements (défilement, menus) sont dans `scripts/commun/entete.ts`.
- Connexion et inscription : gabarit `Base` avec `enveloppe="auth"` (fond, en-tête réduit, pas de pied de page) ; `auth-data.js` est réparti entre `lib/documents-legaux.ts` (résumés des documents), `lib/retour.ts` (pages de retour, icônes des actions), `@vysora/shared` (pseudos, mots de passe courants) et `scripts/auth/commun.ts` (domaines, messageries).
- Accès aux actions réservées (`commun.js` : `exiger`, `accesBloc`, `invitation`, gardes de liens) : messages dans `lib/acces.ts` (mêmes textes que le prototype), dialogue et gardes dans `scripts/commun/acces.ts` (chargé par toutes les pages), bloc rendu par le serveur avec `components/AccesBloc.astro` (le contenu permis en emplacement, le message sinon). Un bouton ou un lien réservé porte `data-exige="contribuer"` et `data-exige-quoi="voter"` ; les liens vers `/creations/nouvelle` et `/forum/nouveau` sont gardés d'office. Les boutons `data-acces-bouton="email"` et `"conditions"` (bandeau, dialogue, paramètres) appellent l'API ; après l'acceptation, l'état est mis à jour sans rechargement (`etats.appliquer`, `etats.on`), sauf si la page contient un bloc d'accès rendu par le serveur.
- Pages légales : `components/PageLegale.astro` rend l'en-tête (version, changements, onglets), le sommaire, « L'essentiel » et l'acceptation ; chaque page (`pages/cgu.astro`…) ne contient que ses sections `.lg-article`, reprises telles quelles. Ce que `documents-legaux.js` construisait dans le navigateur (sommaire, numéros, liens de section, typographie) est calculé par le serveur à partir de ce balisage (`lib/pages-legales.ts`) ; `scripts/documents-legaux.ts` garde le suivi de lecture, la copie des liens, l'impression, la mesure d'audience et l'envoi de l'acceptation. Versions, dates et documents à accepter : `GET /api/v1/documents-legaux` (champ `aAccepter` pour le membre connecté).
- Fiche création : les états du prototype (`data-affichage`, `data-statut`, `data-auteur` sur `.creation-shell`) sont posés par le serveur (`donneesMain` du gabarit) ; les dialogues vont dans l'emplacement `fin` du gabarit, après le pied de page, comme dans le prototype. Une action dont l'API n'existe pas encore est masquée (`ACTIONS_OUVERTES`, `lib/creations.ts`), jamais simulée. Les actions de l'auteur (Publier, Dépublier, Supprimer) suivent `fiche-creation.js` ; la publication passe par une fenêtre avec la case de confirmation (RG-17) et la page est rechargée ensuite. « Signaler un contenu » ouvre le dialogue du prototype (`#report-dialog`), dont les motifs sont ceux de RG-100 (`LIBELLES_MOTIF_SIGNALEMENT`) ; le serveur pose `data-signale` sur le bouton quand la personne a déjà un signalement ouvert (`moi.signalementOuvert`). Les bandeaux d'une création masquée reçoivent la date et le motif de la décision (`masquage`).
- Éditeur des créations : `components/EditeurCreation.astro` rend la porte d'entrée (visiteur, compte en lecture seule, création introuvable) et pose les données de la page (référentiels, création de l'auteur) ; `scripts/publier.ts` construit le formulaire, le panneau et les fenêtres comme `nouvelle-creation.js`. Le modèle du prototype (résultats, chemin de prompts et d'étapes) est gardé et converti dans les deux sens par `lib/publier/modele.ts` (`versContenu`, `depuisFiche`) ; les erreurs viennent de `controlerPublication`, rapportées aux champs de l'éditeur (`controler`). Le brouillon s'enregistre dans l'API au fil de la saisie (le prototype l'enregistrait sur l'appareil) ; l'aperçu ouvre la vraie fiche avec `?apercu` (en-tête, pied de page et actions masqués, fiche inerte). La page n'a pas de pied de page, comme dans le prototype (`piedDePage={false}` du gabarit).
- Notifications : la page pose la première page de `GET /api/v1/notifications` dans un JSON (`#nt-donnees`) ; `scripts/notifications.ts` construit la liste, le volet et la vue d'ensemble comme `notifications.js`, avec les textes et les dates de `lib/notifications.ts` (testés). Réglages du panneau Tweaks retenus : volet de lecture (dépliage sous 1 100 px, comme le prototype), regroupement par date, pastille, extraits affichés, aucune arrivée simulée. Le compteur de l'en-tête suit sans rechargement (`afficherNonLues`, `scripts/commun/compte.ts`). L'illustration de la vue visiteuse reprend quatre photos du prototype (`public/assets/avatars/`).
- Mes contenus : `pages/mes-contenus.astro` rend la tête de la page, les onglets (compteurs compris) et la porte d'entrée d'un visiteur (`AccesBloc`), puis pose les données en JSON (`GET /api/v1/moi/creations`, `GET /api/v1/moi/enregistrements`, libellé du niveau) ; `scripts/mes-contenus.ts` construit les panneaux, le menu et la fenêtre comme `mes-contenus.js`. Les conditions de publication d'un brouillon viennent de l'API (`conditionsPublication`, libellés du prototype) ; après Publier, Repasser en brouillon ou Supprimer, la liste est relue dans l'API. Les vignettes montrent l'image du résultat, sinon le texte ou le code obtenu (comme la fiche), sinon le début du premier prompt.
- Modération (MOD-02, EC-19, maquette validée par le porteur du projet le 25 octobre 2026) : `pages/moderation/signalements/index.astro` (file) et `[id].astro` (dossier d'un contenu, identifiant du contenu), rendues par le serveur, dans le style du prototype : tête de page de Notifications et de Mes contenus, lignes à filets, panneau clair « Pour reproduire » pour le formulaire, fenêtre de confirmation ; feuille `styles/moderation.css` (préfixe `md-`, nouvelle, pas reprise du prototype). Le formulaire ne propose que les décisions de `actions` (calculées par l'API) et `scripts/moderation.ts` contrôle la saisie avec `schemaDecisionModeration` avant l'envoi. Libellés, adresses et textes de confirmation : `lib/moderation.ts`. Le bandeau de la fiche masquée vue par la modération mène au dossier (`moderation.html` du prototype).
- Explorer (DEC-01) : `pages/explorer.astro` rend l'index et, avec `?guide=`, le guide d'un objectif, avec les fonctions de `lib/explorer/` (`index-guides.ts`, `guide.ts`, `elements.ts`, `recherche.ts`), qui produisent le HTML du prototype (`guideRowHTML`, `renderGuide`…) ; `scripts/explorer.ts` reprend ces mêmes fonctions pour la recherche pendant la saisie, les domaines, le tri et le passage d'une vue à l'autre sans rechargement (le guide demandé est lu dans l'API, gardé ensuite en mémoire). Données posées en JSON (`#ex-donnees` : index, guide, outils du référentiel). La recherche d'un objectif reste dans le navigateur (comme le prototype) ; « Parcours qui correspondent » interroge l'API. Mêmes mots vides et synonymes des deux côtés (`@vysora/shared`, `recherche.ts`). « Mes outils » et la liste de contrôle d'un visiteur restent dans le navigateur ; celle d'un membre est dans son compte. Réglages retenus : aperçu qui suit la recherche, index détaillé, méthode en chemin, méthode d'abord.
- Avatars : `components/AvatarMembre.astro` (photo, ou silhouette par défaut) ; outils et modèles avec leur logo : `components/OutilsIa.astro` (`toolHTML` du prototype).
- Accueil (ACC-01) : le balisage de `index.html` a été converti une fois en Astro par un script (routes, adresses des images, typographie française appliquée au texte), puis ses zones dynamiques branchées sur `GET /api/v1/accueil` et les référentiels ; les textes statiques (constat, méthode, profils illustrés, engagements, questions fréquentes) sont ceux du prototype. `lib/accueil/` produit le HTML du prototype (`cardHTML`, `feedHTML`, `renderChart`, `renderBoard`…) pour le serveur et pour `scripts/accueil.ts` (onglets, parcours des cartes, cas, fil relu, courbe) ; les animations de décor sont dans `scripts/accueil/` (vagues du héros, constellation et trame, sphère des outils). Les simulations du prototype (chiffres, fil et classement qui montent au hasard) ne sont pas reprises. L'en-tête de l'accueil a deux logos (`brand-fonce`, `brand-clair`), comme le prototype.
- Profil (PROF-01) : `pages/membres/[pseudo].astro` rend tout le profil avec `lib/profil/` (`renderHero`, `renderCreations`, `renderProgression`… du prototype) ; `scripts/profil.ts` reprend ces fonctions pour les filtres, la courbe, l'aperçu d'une création (sa fiche lue dans l'API) et la modification du profil. L'aperçu public est une adresse (`?vue=public`), la progression n'est rendue que pour le propriétaire.
- Logos des outils dans un texte (`withLogos` de `commun.js`) : `lib/outils-texte.ts` (`avecLogos`, avec les alias du référentiel).
- Reste à porter de `commun.js` quand une page en aura besoin : recherche globale, aperçus de créations d'Explorer (cartes d'une page de domaine).
- Les aperçus « mock » du prototype (fausses captures d'applications) illustrent des créations fictives : en production, une création montre ses vraies images. Pour les données de démonstration, voir le registre (DEMO-01, DEMO-03).
- Images : le prototype écrit `assets/images/<nom>-720.webp 720w, <nom>-1280.webp 1280w` ; une page portée écrit `src={media.url}`, `srcset={srcsetImage(media)}` (`@vysora/shared`), `width`/`height` de `MediaApi` et le texte alternatif reçu, avec l'attribut `sizes` du prototype. Les avatars (`assets/avatars/<pseudo>.webp`) deviennent `membre.avatar` (adresse, ou icône par défaut si null).
